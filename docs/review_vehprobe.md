# Review: UVB, one sphere about a moving vehicle before its mass points' queries

**What:** each tick a moving vehicle's physics asks, for every mass point (22 on a banshee), a ground query (`collision_get_features_in_sphere` about the point, in `compute_ground_plane`) and, in the new physics, a swept ray from where the point is to where the move takes it (`collision_test_vector` in `physics_update_new`); a point with an antigravity probe casts one more ray straight down. With the keep word `vehprobe`, one sphere is asked first, about the centre of mass, reaching every point's query sphere, its antigravity probe and this tick's likely sweep. When it holds nothing, each ground query whose sphere lies inside it and each ray whose two ends lie inside it is not asked, and takes the answer it gives when it finds nothing. Off by default (Sheepdog01's A/B); campaign only (`PSP_MULTIPLAYER` compiles it off).

**Why it pays:** the tick step that carried the name `unit_verify_vectors` is the vehicles' physics, not `unit_update`'s own body. On a30's first fight the PSP spends about 2.9 moving vehicle updates a tick at 3.4-4.2 ms each [M]; a banshee's physics is 3.46 ms an update, 1.25 of it the ground queries and 1.38 the sweep and integration [M]. In the air nearly every query finds nothing: 91% of a30's banshee updates have nothing within one sphere about the whole vehicle [E]. a10's vehicles sit on the hangar floor: nothing to skip there, and a vehicle on the ground is not probed, so nothing is spent either.

**Why it is exact [D]:**
- *What a skipped query would have written.* `compute_ground_plane` first sets the point's ground plane below the world (`depths_of_hell`), no material and the depth that plane gives, and only a query that finds a feature the point lies in changes them (and the point's volatile bit, which `physics_compute_new` clears first, and the shield of an object it stands on). A skipped query leaves exactly those first values. A ray that is not cast counts as no hit: the sweep's point is not stuck and, when no point hits, the move is taken as integrated, which is what a pass of misses does; the antigravity probe adds no force. Nothing else reads the queries' features or results.
- *The sphere only over-reports.* Its level test is any surface or edge in the sphere (the early-out walk), the same walk the ground query's own `collision_bsp_test_sphere` makes; a ray that meets a surface meets it at a point inside the sphere, and a sphere holding a point of a surface touches that surface (its edge, a vertex, or the face under its centre), so the walk finds it. Its object test walks the collideable objects of every cluster of every leaf the sphere touches (a superset of the leaves a ray inside it crosses, or a query sphere inside it touches) and answers yes for any scenery or machine object (the only object types `_collision_test_for_bipeds_dead_flags` and `_collision_test_for_vehicles_flags` test) whose sphere (the datum's or the port's copy) reaches it, through children and siblings, without the gates either query adds: invisible, no collisions (the ground query skips a scripted no-collision object, the ray does not), dead bipeds, the parent's own type. The vehicle itself and what it carries are passed over, as both queries pass them over. A walk that fills its 256 leaves may have dropped some, so it answers yes.
- *Each skip is checked where it is made*, against the sphere actually walked (`psp_vp_inside`): a ground query only when its whole sphere (its radius and the 1/16 the query adds) lies inside, a ray only when both its ends do (a sphere is convex), with 1/64 kept between them against rounding. So the sphere's size, and the guess of the sweep in it, decide only how much is skipped, never an answer; a sweep that leaves the sphere is cast. Nothing moves between the sphere and the queries (the passes of the sweep move only the vehicle's own trial pose).
- *Marks.* The sphere's walk keeps its clusters apart in a local bitset and leaves no object marks; the skipped queries' marks are missing. The marks (`magic_number`) are read only within one query's epoch, and the play hash and the sleep checksum leave them out (as PRS and the flare test before).

**Keep words:** `vehprobe` (both physics), `vehprobe1` (the new physics only: the banshee's, not the radius physics of the dropship and the Pelican), `vehprobecheck` (the sphere decides, every query is asked anyway, and any query or ray it would have skipped that found something is counted). Every 600 vehicle updates a `vehprobe:` line gives the updates by physics, how many were probed and found nothing, the ground queries and rays skipped and asked, and the check's count.

**Key lines** (psp_fixups.py, `FIXES_VEHPROBE`): `collisions.c#vehprobe` adds `psp_vehprobe_reach_empty` (the level's early-out walk, then the object walk in `psp_vehprobe_object_reaches`); `physics.c#vehprobe` adds the sphere (`psp_vp_begin`, before `physics_compute_new` and at the top of `physics_update_old`), the inside test, the guarded ground query in `compute_ground_plane`, the guarded rays (the sweep and both antigravity probes) and `psp_vp_end` before the unit collisions.

**Cost and risk:** one sphere walk and one object walk a probed update; nothing for a vehicle on the ground last tick. Touches hot tick code (`compute_ground_plane`, the sweep loop) by one test each when off. The changed functions' PGO counts no longer match until the next profile, so a `PSP_PGO_STRICT=1` link lists them. Campaign only.
