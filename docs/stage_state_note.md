# Stages need a world that holds still: the shared state that walls the tick's stages

`cpu_cost_map.md` §4's "Phasing / stage-major" row and §4a size what running the tick's big code stage by stage over every object could save. Every row there stops at the same kind of wall: a stage's output is read by something later in the same tick, either inside the same object's update or by an object updated after it. This note asks which shared state, if other objects read it from a copy made at the tick's start (the last tick's copy, double-buffered) instead of live, would take those walls down, and what that costs against the multiplayer boundary (`exact_state.md`, ledger 7) and the job graph's reads and writes (`job_graph.md`, ledger 6).

Labels: [M] measured on a PSP, [E] emulator or cache model, [D] read in code (the engine at the pin, d98982b; `psp_fixups.py` at tock162 059d1ccf), [U] inference. Started 2026-11-04 for the master's 23:15 items.

## 1. Headline

**The walls are four pieces of shared state, and one of them carries most of the prize.** What later objects read from earlier ones during `objects_update` is (a) **the world view collision reads**: each object's position and bounding sphere, the clusters' collideable lists, attachments and node matrices, the same five writers that already bump `psp_object_epoch` for perception's rays [D, `psp_fixups.py` FIXES_121 `objects.c#epoch`]; (b) **the global random seed's draw order**; (c) **the object and effect pools' allocation order** (datum indices); (d) **damage written into another object** (vitality, death). The AI adds (e) its shared records (props, encounters, squads, the timeslice).

- **(a) read from the tick's start** is the one change that lets collision run as a pass of its own and lets node matrices be made stage-major without nwbatch's read-through hooks. Collision is the only big subsystem whose code fits the I-cache as one pass (~180-255 code lines a tick), and phased whole it is worth ~0.75 ms a tick on b30 and ~0.54 on c20; node matrices made stage-major are worth ~0.7-0.95 on b30 and ~1.1-1.2 on c20 [U on E, `cpu_cost_map.md` §4a]. Together (they overlap) that is the largest prize left once the bipeds are out. It is **not exact**: a collision query today sees objects earlier in the walk at this tick and later ones at the last. So it changes campaign play and needs Sheepdog01's call (collision stays exact by the project's rule: Sheepdog01 10-30, "one path, every mode", `exact_state.md` §3). On a multiplayer client it stays inside every bound the host checks: the own unit's 3.5 units, the vehicle's 5.0, a hit report's target within 3.0 + 15 ticks' movement [D, `exact_state.md` §2].
- **(b), (c) and (d) can't be double-buffered**; they can only be kept in order (a log replayed in the walk's order) or given up (a seed stream per object). The seed and allocation order are local to the client (`exact_state.md` §2: randomness, the client's own objects), so giving them up is a campaign-play question, not a multiplayer one.
- **The AI already reads a still world.** `ai_update` runs before `objects_update` in `game_tick` (game.c 342, 369) [D], so every actor sees the objects as at the tick's start, and AIME already thinks a tick ahead with its own seed. What walls its stages is (b) and (e), not (a).

## 3. What the copy would be

**The world view (a), as of the tick's start.** Collision and perception read, for every object other than the one asking: its position, bounding sphere and cluster references; the clusters' collideable lists; its parent and children; its node matrices. The copy would be:

1. **Positions, spheres, cluster references:** a tick-start array of each collideable object's 16-28 bytes, written whole (`cache 24`) at `objects_update`'s start. Small: ~200 collideable objects on c20 is ~5 KB [U].
2. **The clusters' collideable lists:** two partitions, one read (last tick's), one written (`object_reconnect_to_map` writes the next). Swapped at the tick's end. Today a reconnect disconnects and reconnects in full and keeps list order (the relink memo's note); a second partition doubles that table and adds its swap [U: size it from the cluster partition's pool].
3. **Node matrices:** the record already copies them for the replay (up to 64 nodes a model, `job_graph.md` §5), and VISLAZY makes most of them only when read. A collision read from last tick's matrices needs those matrices kept, not recomputed: a node block per collideable object held one tick longer. This is the largest of the three (52 bytes a node; c20's bipeds ~446 nodes in the update [D, PNC row]) [U].

What it buys: collision queries can be batched and run as one pass of their own (its code fits: `cpu_cost_map.md` §4a). One limit stays: an object's own queries chain (a biped's sphere tests each feed the next), so a pass of its own takes each stage's first query from every object, and the rest run inline beside the stage's code, which must then fit with it; node matrices can be made stage-major after the walk without hooks, since no other object reads them live (NB's lesson: its hooks cost ~5% of c10's tick even off [M]); and moves (`object_translate`) stop being order-sensitive for every other object. The ME's AI job and its rays already pay for a coherent view by waiting (`psp_object_epoch`, the rays' five writers): with a tick-start copy they could read it without waiting.

What it doesn't buy: (b) the seed's draw order, (c) allocation order and (d) cross-object damage. Of these, (d) is the game itself (who is hit first decides who dies) and stays in walk order. (b) and (c) could be kept exact by logging and replaying in walk order only where nothing reads the result inside the stage; a weapon reads the projectile it allocates (its owner and parent set at once), so (c) needs a reserve-then-fill pool, not a log [U].

## 4. Against the boundary (ledger 7) and the job graph (ledger 6)

- **Exact boundary:** nothing in (a) crosses the wire. It reaches the host through the own unit's prediction (bounded 3.5), the own vehicle (5.0) and hit reports (target within 3.0 + 15 ticks' movement, impact within 2.0) [D, `exact_state.md` §2]. A one-tick-old view of *other* objects moves a hit by at most one tick's movement, inside those bounds [U]. The riskiest call is the one ledger 7 already names: node, region and material in a hit report come from node matrices, and whether the host bounds them is open (`exact_state.md` §4 item 1). A tick-start copy keeps the matrices exact, only older, so it adds no bias of its own [U].
- **Clock:** the copy and the swap add work every tick; the tick may run long but never fast, so the host's clock check is safe [D, `exact_state.md` §2].
- **The job graph:** the AI job runs across `game_frame`, the record and the next loop's rest, and must be collected before `units_update` and `game_allegiance_update` write what it read (`job_graph.md` §5). A tick-start copy of (a) is exactly what that job reads already, so it would let the job read a copy instead of the live pools, and drop its whole-cache write-back before and the pool hash check after [U]. The rays' wait on the five object writers (`job_graph.md` §5) goes too.
- **Campaign play:** every use of (a) changes the campaign's play (statecrc diverges at the first query that sees a moved object), so it ships only as a compromise under Sheepdog01's rule: built off behind a keep word, A/B'd, side-by-sides showing it plays the same. Collision's exactness is a project rule today, so this is Sheepdog01's decision before any build.
