# The main CPU's cost map

Where the main CPU's time goes, the rules the hardware sets, and how far each way of cutting the cost has got. **Read this before proposing a speed lever**, alongside the lab's `tools/levercheck.py` history for the lever's ground. A proposal names the line of section 4 it attacks, that line's ceiling, and what's different from the tries already listed there.

Labels: [M] measured on a PSP, [E] emulator or cache model, [D] read in code or docs, [U] inference. Each figure gives its source, so it can be checked and replaced. Section 6 says how this page is kept current.

Started 2026-11-04 (Sheepdog01: "we need to use it to guide our steps so we aren't firing into the dark every time we try a new lever").

## 1. Where the time goes

**The main CPU binds the heavy maps.** Its cycles fall into three phases, each either working or asleep [M, tock159 ladder, PSP-1000, lab sierra-hw 41821725723, the `hardware by phase` lines]:

| Map | Tick | Drawing | ↳ drawing asleep | Other | ↳ other working |
|---|---|---|---|---|---|
| b30 | 58% | 36% | 3% of the clock | 5% | 5% |
| c20 | 53% | 35% | 7% | 12% | 11% |
| d20 | 46% | 44% | 10% | 10% | 10% |
| a50 | 48% | 42% | 2% | 10% | 9% |
| c10 | 37% | 55% | 2% | 9% | 8% |
| a30 | 23% | 67% | 16% | 10% | 9% |

- **Tick:** pure CPU work; asleep ~0%.
- **Drawing asleep:** on d20 it is the wait for the ME's render job (the replay). That job grows to ~65 ms of the ME a frame (91% of it) from game time ~1,800, and the main CPU then waits 14–17 ms a frame for it. Before game time ~1,200 the wait is ~0. The GE's own finish is ~1.6 ms a frame, and the ring's waits are ~8 µs a job [M, PSP-1000, lab sierra-hw 41821725723 and 41888761035, 2026-11-04]. The steady second half is probably the player standing still on one heavy view (no route) [U]. On tock162 the same pair makes the other maps' sleep: c20's 3.5 ms a frame is the replay's wait 2.2 plus the GE's 1.3, b30's flight 2.9 is 0.3 plus 1.8 [M, `frame_timeline.md`].
- **Other, working:** on d20 it is 6.2% of the clock, all on the game's own thread (96.5%), about a quarter of it in the kernel (system calls, firmware). Its code is the frame's game work outside the tick [M, PSP-1000, lab sierra-hw 41888761035, `pcsampleother`, 2026-11-04]:
  - particles and point physics, about a third: `particles_update` 8.6%, `bsp3d_test_point` 8.0%, `collision_bsp_test_vector_recursive` 5.8%, `psp_point_physics` 3.2%;
  - `tag_get` 4.6%, `game_time_update` 3.8%, looping sounds 2.4%, the weather palette 1.6%.
  - **Its system calls, by name** (2026-11-11) [E counts, lab syscall2 b30; the lab's `docs/research/fw661/firmware_side_review.md` has each caller and what 6.61 does in it]: 258 calls a tick, 129 of them in this phase, 117 of those clock reads (153 clock reads a tick in all: `GetTickCount` 71, `SDL_GetTicks` 18). A call that does nothing costs 0.54 µs with its path resident [M, PSP-1000, fwbench round 1; `hardware_facts.md`], so the dispatches alone are ~0.14 ms a tick (258 x 0.54) and the rest of the calls' cost is the routines themselves and the lines they push out; only the count is avoidable (the dispatch is Sony's, ~100 instructions). GETTICKCACHE, which took 70 of them, measured slower on the PSP.
- On the light maps (b40, c40, d40, a10), "other" is 33–50% of the clock and mostly asleep: waiting for the display refresh, which is headroom.

**By box and by cause: the frame picture (2026-11-17, provisional until its identity check passes) [M, PSP-1000; the table's home is the lab's REBUILD.md §3.5, rows frame_picture_*_1000; design docs/frame_picture.md].** Each box's time comes from marks at its entry and exit, at <= 1% cost. Its wait is split by miss counts x prices measured the same day (code 56, data 51 clean / 97 dirty, uncached load 39 cycles; GE idle), as a range:
- **The tick is the objects' update:** 20.5 ms a tick on b30_leg2 (work ~7.5, code wait ~5.0, data 3.1-5.9, unexplained 2.0-4.8), 23.9 on c20_leg2 (~85% of the tick; code 6.7, data 3.0-5.7, unexplained 4.3-7.0), 15.1 on b40_leg1, 10.3 on c40's pad. Over half of it is waiting on memory, ~~code about as much as data~~ **code more than data** (refiled below, 2026-11-17).
- **The ME's trade, on c40:** it takes ~21.6 ms a frame of the world's render off the main CPU (27.5 ms with it off, 5.9 on), and its traffic slows the main CPU's objects by ~1.4 ms a tick (+15%) and render objects by ~0.9 ms a frame.
- **Effects' drawing** is 4.1 ms a frame on b40, three-quarters of it work.
- ~~**"Unexplained"** (1-7 ms a tick) is the wait no GE-idle price covers: the GE's and the ME's contention for main RAM, and price error. Prices taken with the ME busy will split it (the lab's framepic-mebusy).~~ **Superseded 2026-11-17 (the splits refiled at loaded prices; docs/frame_picture.md, the lab's row framepic_splits_refiled_loaded) [U on M]:** at the GE-35% prices (code ~77, data ~75-137, uncached ~59 cycles) times the ME's toll where it ran (x1.04-1.14, hardware_facts.md), what's left is -1.5 to +1.2 ms a tick, zero inside every box's range: the stalls are all code and data misses, at 1.03-1.57x the idle price (ME off 1.05-1.22x, the ME-on tick boxes 1.27-1.57x). No GE+ME bench is needed.
- **The objects' update waits more on code than on data on every stretch** [U on M]: code / data ms a tick, b30 7.2-7.9 / 6.0-6.6, c20 9.6-10.5 / 5.9-6.5, b40 5.7-6.2 / 4.2-4.6, c40 ME on 4.1-4.5 / 3.1-3.4, ME off 3.7 / 2.7. The drawing is the other way. So for the object boxes (biped motion, posing, collision), less code run a tick ranks ahead of data layout: the I-misses are >90% capacity and code layout is spent (§3), so the levers are smaller code, stages that fit the cache, and cheaper fills (VRAMCODE), not code rearranged.

**What a 15 ms tick asks of the wait (2026-11-16) [U on M]:** on b30's flight the tick is ~14.4 ms of work and ~25.5 ms of memory wait (the lab's `whole_frame_memory_wait_ms`). Halving both gives 19.95 ms, and a third of the wait plus half the work gives 15.7. A 15 ms tick needs the wait at ~7.8 ms (~31% of today's, ~27,000 misses at the in-tick ~97 cycles) with the work halved. Three outside reads (Kimi K3.1 Pro, DeepSeek V4.1 Flash, GPT-6 Astra Pro; the lab's `research/outside_eyes/read_round2_2026-11-16.md`) each worked this out, correcting the briefs' "half the wait".

**Inside the work, memory dominates.** The tick waits on memory for 54–68% of its own cycles (b30 63%, c20 68%), drawing for 47–60% [M, same lines]. The tick's misses are all cached ones; its uncached accesses are ~50 a million cycles. On b30 that's roughly 11 ms of an 18 ms tick spent waiting [U, the share times the tick].

## 2. The machine's rules

| Rule | Figure | Source |
|---|---|---|
| Caches | 16 KB I and 16 KB D, 64-byte lines (256 each), 2-way (8 KB a way), write-back with a write buffer, no L2, nothing snoops | `psp_hardware_reference.md` §1; `research/research_icache.md` (2-way) |
| A miss | ~73 cycles for a random line, ~57 for a sequential one | [M, halo_bench v7, v9] |
| No overlap | The core is in-order: it stalls at the missing load (only ~10 cycles of work slip under a miss), never has two misses in flight, and has no hardware prefetcher | [M, v7, v9] |
| Prefetch, data | `cache 30` (Fill, 0x1E) is a real, non-blocking prefetch. It pays only with ≥ ~70 cycles of independent work before the use. While a fill is in flight, every other load and store waits for it, and fills don't overlap each other. There's no MIPS `pref` (`__builtin_prefetch` compiles to nothing) | [M, v7b, v7c, v9]; `prefetch_map.md` |
| Prefetch, code | None from user code: `cache 0x1E` fills no I-cache line, and the I-side op raises "coprocessor unusable" in user mode | [M, IPREFETCH, 2026-11-02, lab sierra-hw 41571045909] |
| Whole-line writes | `cache 24` (create dirty exclusive, 0x18) makes a line without reading it: half the cost of writing whole lines. Lines not wholly written hold garbage | [M, v9: 1 MB 6,067 → 3,116 µs] |
| Scratchpad | 16 KB, always hits, costs the D-cache nothing, reachable by the CPU and the GE. Uncached, code runs from it at 14.3 cycles an instruction | [M, v9; CODESPAD] |
| The GE shares the bus | CPU misses take +65–96% longer while the GE reads textures from RAM, and +272% while it reads vertices from RAM. Reads from VRAM leave them unchanged. DMA running alongside: 218 → 499 ns | [M, v8b, v7]; `memory_traffic.md` |
| The ME is a second CPU | Its own 16/16 KB caches. Its misses cost the same, and the two CPUs' misses don't slow each other (latency-bound work), so work on the ME roughly doubles the misses the machine serves at once | [M, v10] |
| The compiler | GCC has no Allegrex pipeline model: it won't move loads early to fill a window | [D, `psp_hardware_reference.md` §8] |

## 3. Why the tick misses

- **Capacity, not conflicts.** A fully associative cache would remove only 5–8% of the tick's I-misses on b151 (b30, c20, b40) [E, lab icsweep1 42311430811; 16–18% on the older builds of `cache_work.md`], so over 90% are capacity. The size sweep says the same: a 32 KB I-cache would take 25–40% of them off, 64 KB 53–71%, 128 KB 71–85% [E, icsweep1]. The tick's hot code is ~70 KB, fetched again 47–75 times a tick [E, `cache_work.md`].
- **The data side is capacity too** (2026-11-11) [E counts, lab dcanat1 42989839989, the tock at the shipped recipe, the ME's side apart]. Of the tick's data misses (32,053 a tick on b30's cutscene and flight, 13,039 on c20), 21-22% are conflict misses, ones a fully associative 16 KB cache would have hit, and 78% capacity. A cache with no conflicts at all misses 14-15% less (it loses some hits the 2-way keeps), a 4-way one 11% less, a 32 KB one 27% less and a 64 KB one 43-45% less. So data layout, like code layout, can reach at most ~15% of the data misses, and a footprint cut has to be large to show: halving what the tick touches buys about a quarter.
  - By the missing function's system on b30: collision 28%, AI 13%, other objects 13%, posing 12%, libc 9% (`memcpy` alone 6.4%, the top single function on both maps), bipeds, units and vehicles 6%, data and tag lookups 5%. Conflict is 21-26% in every group but libc (10%).
  - 19% of the tick's fills leave clean with one word used and 14% more with two; collision's walks are the exception (3-12% one word). 6-7% of the misses are on `$sp`-based accesses, three quarters of them stores: a frame's first stores to a line that had left.
  - **What the tick touches** (2026-11-11) [E counts, lab dcanat2 43011966093; the lab's `research/opportunities/footprint.md` has the tables]: 9,428 distinct data lines a tick on b30 (603 KB) and 5,590 on c20 (358 KB), against a cache of 256 lines; a fill has 5.6 of its 16 words used, and the cache turns over ~125 times a tick on b30. By structure on b30, in fills a tick: the program's globals 6,881 (21.5%, from only 825 lines, 3.1 words a fill), the object pool 4,824 (15.1%), tags 4,815 (15.0%), the stacks 3,277 (10.2%: 318 lines, each fetched 10 times a tick), the level's BSP 2,713 (8.5%), the heap 2,560, actors and props 2,262, the collision spheres and cluster references 2,119 from 137 lines, the object header 772.
  - **`memcpy`'s misses are two callers** [E counts, dcanat2]: `psp_aime_think_actor` 1,252 of b30's 2,073 a tick (134 calls, 51.8 KB copied) and `psp_pose_ahead_take_work` 604 (43 calls, 18.6 KB), 90% between them (92% on c20). Both are the copies that hand work to the ME: the copy, not `memcpy`, is what there is to cut.
  - **A few lines carry a lot** [E counts, dcanat2's cache map]: the hottest 256 data lines hold 29.7% (b30) and 35.1% (c20) of the tick's data misses, the hottest 64 lines of program data 10.9% and 13.0%, and the main stack's best contiguous 4 KB at least 5.2% and 5.9%. The scratchpad (16 KB, never missed, out of the ME's and DMA's reach) is the place for such lines: levers SPSTACK (the tick's hot stack on it) and SPADG (the hottest globals; its clean form is blocked, because the small-data area is one 14.8 KB run inside `$gp`'s reach and the ME's side reads it too) in the lab's levers.tsv. Their price is a PSP pair's to give (the cache rule).
- **Layout is spent; size isn't** (Sheepdog01 2026-11-06 18:52) [2026-11-12: spent only while kept fresh: a stale layout or profile costs as much as the largest levers gain (TG's refresh tick -4.6 to -13%, SLEEPDBG +5 to +8% on a stale profile, the posing box +1.3 to +2.0 ms a tick until it had its own profile and layout, then +0.1 to +0.3) [M]; every box cut in moves it; the lab's `research/opportunities/misses_assembled.md` (Sheepdog01's audit, 2026-11-12)]. Over ~30 layout tries are stopped (grouping PGO's hot set HG, a smaller hot set FH, inlining more RL1 or less CI1, -Os on the big updates CI2, the scratchpad CODESPAD, prefetch IPREFETCH ...: the lab's `levercheck.py --ground code-layout`), and the misses are capacity, so moving code doesn't pay. What's left is code the tick no longer runs: X10 (the fatal asserts compiled out) took the tick down 6.6% on the PSP-3000 [M], the one size win so far. The census (recon, deadpaths1-2 [E]): campaign constants are ~2% of the hot functions' never-run bytes, the port's own instruments 20-26%, the rest gameplay branches. The one big size cost was the soft 64-bit helpers behind function values' phase: HUHINT (one cast, exact) took c20's frame down 2-2.3 ms (-3-4%) and its tick 0.6-0.8 ms (-3%) on the PSP [M, sierra-hw 42342168318 + 42342911261].
- **The big updates are bigger than the cache on their own** [E, `cache_work.md` §1, c20]: one `object_update` call runs 365 code lines (78 calls a tick), `biped_update` 299, `unit_update` 68 (384 over its 29 calls). The cache holds 256 lines.
- **Data misses by region** [E, `cache_work.md`, b30]: game state 37% (the object pool alone 16%), the tag window 32%, program globals 19%, thread stacks 10%, heap 2%.
- **By function:** `collision_bsp_test_vector_recursive` 6.6%, `object_get_and_verify_type` 4.9% (TYP took it), `psp_bsp3d_test_sphere` 4.6%, `cluster_partition_get_next_datum` 3.1%, `object_compute_node_matrices` 2.5% [E, same].
- **The exchange rate:** 1% fewer tick I-misses ≈ 0.3% of the tick [M against E, PGO in b116; `research/research_icache.md` §0].

How to read it:
- **Its own pair:** the subsystem's whole calls on a second 16 KB pair. The main CPU's drop is what the subsystem costs; what the pair still misses is what it costs run whole as a pass of its own. "Whole" is the difference.
- **In stages that fit:** the drop less one fetch of its code lines a tick (each stage ≤ ~200-256 lines, resident over every object), less the data price. The data price is calls × its own data lines a call (not touched by an earlier call) × ~half re-fetched × (stages − 1).

- **Overlap:** the ceilings overlap and don't add. Collision's calls run inside the bipeds', vehicles' and projectiles' updates; held weapons and riders update inside their parent's `object_update`.

## 5. What the record teaches

- **The cache model undersizes cache wins on the PSP**, 2–3× for code size and layout: X10 scored −1.8% in the model and measured −6.6% [M]. [weaker, 2026-11-12: one case, X10; the model's miss counts match the PSP's within ~10-12%, and HG, FH, CI2 and HUHINT agreed in direction and rough size; the lab's `research/opportunities/misses_assembled.md` (Sheepdog01's audit, 2026-11-12)] Cache work is priced on the PSP (the lab's CLAUDE.md).
- **But a split's ceiling overstates what a restructuring gets.** Giving code its own cache shows the most grouping could save, not what a given shape reaches. Node-matrix phasing scored −11.5% and lost 34% on the PSP. Slice 3's ceiling was −26%, and it got −1.4% I-misses and a loss [M]. A ceiling says the prize exists; a built shape in the cache model is the next check, and the PSP the last.
- **The emulator's drawing is short on d20 and b30** (B58): its level materials wait for copy room that the PSP always has, so emulator drawing figures there undercount (the light pass ~8× on d20). Check a PSP log for "level copies short of room" before trusting one.
- **Staging costs data.** Each stage writes its results out and the next reads them back. With I and D near even in cost, a restructuring has to price both from the start (slice 3).
- **Small fixes to scattered misses don't add up.** A miss at a site with no window can't be hidden. What pays is changing the shape of the work: fewer distinct lines per pass, loops regular enough to prefetch, buffers written whole.
- **Where things point:** packing is near its ceiling, prefetch is a hand tool that needs reshaped loops, and reuse comes in small steps. The large remaining ground is restructuring the tick around the cache, with its data price counted. That is why the rebuilds (the drawing rebuild, the ME scheduler, the tick) keep coming up.

- **At 30 fps a frame is one tick.** Once-a-frame levers (FX15, RENDERTICK) are worth nothing at the target, and the GE's toll on the tick grows with the frame rate, so price a lever at the target, not at today's frame rate.
- **Code layout is spent** (while kept fresh: see §3, 2026-11-12)**:** ~30 tries, and I-misses are >90% capacity misses. Propose code the tick no longer runs, not code arranged differently.
